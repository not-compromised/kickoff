# Kickoff security invariants

These are the standing security rules. The code must satisfy them at every moment, whatever feature just ran, and each one is a release requirement. `scripts/check.sh` runs every named test, then every **mutant**. The release pipeline refuses a build if any row is failing, skipped or missing, or if any of a row's mutants passes its test (SI-33).

Columns:
- **Rule:** the maintainer's sentence.
- **Enforced by:** the test, plus a runtime check or lint where one exists.
- **Mutant:** the mitigation removed. The named test must **fail** against it, which proves the test detects that removal (round 2 found several tests that would have passed without their mitigation).
- **Born from:** finding ids, `docs/reviews/r1-*.md`, `r2-sol.md` and `r3-sol-m1-facts.md` (R3-n).
- **Scope:** the platforms where the rule holds. A row that does not hold on a platform says so, and §1.2 of the design must not claim it there.
- **Held:** the milestone that must turn it green. The project is in design, so none hold yet.

Design references are to `docs/design.md` draft 3. Class letters refer to its §6.2.

Mutants are of two kinds:
- **Build mutants** are cargo features named `mutant-si<N>-<slug>` that compile the mitigation out. They are never enabled in a release build, which a release check enforces.
- **Configuration mutants** are documented broken setups run in the VM or namespace suites, for example a gamebox with the host X socket mounted.
